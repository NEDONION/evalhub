# 专业六边形评测集建设与交付复盘

## 文档定位

本文沉淀 `evalhub-hexagon-v1` 从需求澄清、专业数据集选型、固定样本构建、评分安全、
可复现工作流、前端呈现到分支合并的工程经验。目标不是重复接口说明，而是回答：

- 为什么这样设计。
- 哪些边界一旦省略就会产生不可比较或不安全的结果。
- 下次新增专业评测集时应按什么顺序实施和验收。

正式协议与实现细节仍以
[Hexagon v1 设计](../superpowers/specs/2026-08-04-evalhub-hexagon-benchmark-v1-design.md)、
[实施计划](../superpowers/plans/2026-08-04-evalhub-hexagon-benchmark-v1.md)、
[系统架构](../architecture/20260804_系统架构.md)和代码为准。

## 一、先定义比较目标，再选择题目

### 1. 六边形是比较协议，不只是图表

能力轴固定为知识、指令遵循、数学、综合推理、代码、安全可信。固定名称、顺序和含义后，
不同模型的图形才可直接叠加；临时更换轴、题量或聚合权重会生成另一套协议，不能沿用原排名。

### 2. 小样本的价值来自固定和覆盖，而不是伪装成全量榜单

套件初始 `1.0.0` 协议固定 60 题；`1.1.0` 将规模缩减为 30 题，当前 `1.2.0` 在同一选题上增加
模型生成与答案评分兼容协议：MMLU、IFEval、GSM8K、
BBH、HumanEval 各 5 题，TruthfulQA 3 题与 BBQ 2 题共同形成安全可信维度的 5 题。两个版本
使用不同清单摘要和协议指纹，不能混排。Mini Suite 适合频繁回归和同配置横向比较，但不替代
原始数据集的官方全量成绩。

题量较小时，必须优先保证：

1. 六个维度都有独立证据。
2. 选题过程可重建，最终题目又不会随上游顺序漂移。
3. 每个模型运行完全相同的题目、提示和评分器。
4. 报告明确标识为 EvalHub 固定 Mini Suite，而不是官方全量榜单。

### 3. 只从专业公开数据集抽题

自编题适合产品演示，不适合声称专业可比。专业评测应保存上游项目、许可、固定 revision、下载
地址和文件 SHA-256。来源的知名度不能代替版本证据；同名数据集的不同镜像、分支或清洗版本
可能已经是不同试卷。

## 二、把“选了哪些题”做成不可变资产

### 1. 固定来源合同

每个来源至少绑定以下四项：

| 字段 | 作用 |
| --- | --- |
| `source_id` | 对应 EvalHub 中稳定的 Benchmark ID |
| `url` | 下载的具体文件，而不是项目首页 |
| `revision` | 上游 commit 或可审计版本 |
| `sha256` | 校验实际下载字节 |

下载流程应先写临时文件，校验摘要后再原子替换缓存。不能把“HTTP 200”视为准备成功，也不能在
摘要不匹配时继续使用旧缓存。

### 2. 选择算法和最终清单承担不同职责

- 构建脚本负责确定性分层抽样，证明选择过程可重放。
- 提交到仓库的 manifest 固定当前协议的全部 source key、顺序和展示元数据。
- CI 或交付验证重建 manifest，并与已提交文件做字节级比较。

只保存随机种子不够：上游数据增加、排序变化或解析器升级后，同一随机种子仍可能选出不同题目。
因此运行时必须消费固定 manifest，而不是每次重新抽样。

### 3. 数据身份需要多层摘要

可复现运行至少需要区分：

- 上游 revision：说明来源版本。
- 下载文件 SHA-256：说明本地使用的真实字节。
- manifest SHA-256：说明选择了哪些题以及顺序。
- 协议指纹：说明提示、生成参数、评分器和聚合方式。
- verifier 身份：说明代码题实际由哪套可信执行文件评分。

这些值不能互相替代。只固定数据而不固定评分器，成绩仍会漂移；只固定 manifest 而不校验源文件，
同一个 source key 也可能解析出不同内容。

## 三、英文执行与中文展示必须是单向边界

需求是“模型跑英文，中文给人看”。实现时应把它当成数据隔离规则，而不是 UI 偏好：

- `input`、官方选项和模型提示只保留英文执行内容。
- `input_zh`、`reference_zh` 只作为展示元数据持久化。
- Adapter、Evaluator 和 HumanEval 沙箱不读取中文翻译。
- UI 明确标记中文为非官方翻译，避免被误认为数据集原文。

必须测试模型适配器收到的真实字符串，而不是只检查 manifest 字段。否则中文虽然名义上属于 metadata，
仍可能在模板拼接时进入提示，导致与官方英文协议不可比。

## 四、评分器按任务语义分层，不追求一个万能入口

### 1. 文本任务复用公共 Runner

多选、精确匹配等任务应继续走现有 Adapter、Runner 和 Evaluator 边界。新增数据集时优先增加格式
转换和 Evaluator 注册，不在 Runner 中按数据集名称堆叠分支。

### 2. IFEval 必须执行官方规则语义

IFEval 不是普通字符串相等。每个样本携带 instruction ID 和 kwargs，评分前应验证所选规则集合及
参数形状，再按固定实现分发。未知规则必须阻塞，不能默认失败为零分，否则基础设施缺口会被误写成
模型能力不足。

### 3. HumanEval 必须使用专用可信边界

生成代码是非可信输入，不能在 EvalHub 宿主 Python 进程执行。安全边界至少包括：

- 固定基础镜像 digest 和 verifier 文件身份。
- 无网络、无宿主目录挂载、只读根文件系统。
- 非 root 用户、移除 capabilities、启用 `no-new-privileges`。
- CPU、内存、PID、输出和时间限制。
- 控制器持有隐藏测试，worker 只接收完成单次判题所需的最小数据。
- 无论成功、超时还是协议错误都回收容器。

HumanEval 的基础设施错误应标记为 `blocked`，而不是产生 0 分。模型候选执行失败才属于模型结果。
“Docker 不可用时降级到宿主执行”看似方便，实际会同时破坏安全性和评分协议，必须禁止。

## 五、任务创建时冻结协议，恢复时拒绝漂移

### 1. 冻结发生在创建时

工作流节点应保存创建任务时的 Benchmark 规格、来源合同、manifest 摘要、提示模板、生成参数、
Evaluator 类型和 verifier 身份。最终结果发布这些冻结值，不能在任务结束时重新读取当前 Registry，
否则一次长任务可能混入两个部署版本。

### 2. 恢复不是“有 checkpoint 就跳过”

恢复前应再次核对：

1. 当前源文件摘要是否仍与准备节点一致。
2. manifest 是否仍是任务创建时的版本。
3. 样本输入与结果中的协议指纹是否同时匹配。
4. HumanEval verifier 身份是否匹配。

任一不一致都应清除受影响的样本跳过集合并阻塞或重算。复用不匹配 checkpoint 比重新运行更危险，
因为它会生成表面完整、内部混合的成绩。

### 3. 排名只接收完整可比较运行

Hexagon 排名应要求：

- `sample_mode=all`。
- 七个来源全部成功，六个维度都有成绩。
- suite、manifest、来源、提示、生成和评分协议指纹一致。

部分运行可以用于诊断和预览，但不能与完整运行进入同一排名。缺失维度也不能按 0 分填充，因为
“未评测”和“能力为零”是不同事实。

## 六、API 与 UI 要展示证据，而不泄漏判题材料

### 1. 就绪状态使用结构化合同

一次合并暴露了两个并行接口：旧 Harness 返回 `(ready, reason)`，新 Hexagon 返回
`ExecutorReadiness`。如果 API 消费者同时假设两种形状，就会出现错误解包或整批“未配置”。最终经验是：

- 内部统一为 `ready`、稳定 `code` 和安全 `message`。
- 核心 Harness 与 Hexagon Docker 探测在共享边界汇合。
- API 同时保留兼容字段和结构化 readiness，前端不自行猜测。

### 2. 样本详情是证据账本

建议展示英文题目、中文翻译、模型输出、分数、状态、来源和 source key。HumanEval 隐藏测试、官方
canonical solution、环境信息、堆栈和原始私密结果不得进入 API 或 DOM。即使旧数据库含有额外字段，
presentation 层也应使用允许列表重建响应，而不是删几个已知敏感键。

### 3. 前端显示必须区分“未就绪”“部分完成”和“可比较”

执行器未就绪不是题目未下载，部分完成也不是完整评测成功。颜色和文字可以简洁，但状态含义必须
来自服务端事实。前端只负责呈现，不重新实现排名或 readiness 规则。

## 七、测试与交付门禁

### 1. 单元测试不依赖真实外部环境

数据下载、Docker、Ollama、lm-eval 和网络状态都应在边界处替换为精确 fake。单元测试验证：

- 固定来源和 manifest 校验。
- 七种数据格式到公共样本的转换。
- IFEval 规则分发和拒绝未知规则。
- checkpoint 失效与恢复。
- readiness、错误分类、排名准入和 API 脱敏。

### 2. 外部集成单独显式运行

HumanEval Docker 测试需要真实 daemon，应通过显式环境开关运行并单独报告。不能因为默认测试显示
`skipped` 就声称 Docker 已验证；也不能因受限沙箱禁止访问 Docker 就误判实现失败。

本次最终合并在 `main` 上实际通过：

- 常规后端：313 passed，9 个 Docker 用例按默认策略 skipped。
- Docker 集成：9 passed。
- 前端：77 passed，生产构建通过。
- Ruff、Shell 语法、manifest 字节重建和 `git diff --check` 通过。

### 3. 先区分产品失败与执行环境失败

全量测试曾因受限执行环境禁止绑定 `127.0.0.1` 而出现 9 个 `PermissionError`。同一命令获得回环
权限后全部通过。正确做法是阅读堆栈、定位失败边界并在允许的环境复跑，不修改产品代码来迎合沙箱。

## 八、分支合并经验

### 1. 冲突要按语义合并，不能整文件选边

功能分支开发期间，`main` 同时接通了完整行业 Benchmark。冲突集中在 Registry、readiness、任务
分发、运行时和前端类型。两边都正确，但面向不同套件；选择 `ours` 或 `theirs` 都会丢功能。

正确顺序是：

1. 列出冲突文件和分叉后的提交。
2. 找出两边各自维护的公开行为。
3. 先合并两边测试，形成联合契约。
4. 用最小分发条件让核心 Harness 与 Hexagon 专用路径并存。
5. 运行相关测试，再扩大到全量门禁。

### 2. 合并后要检查自动合并产生的重复定义

Git 能自动拼接文本，但不理解符号唯一性。前端构建捕获了两边各自新增的 `BenchmarkExecutor` 重复
定义。经验是：冲突标记清零不等于合并完成，必须继续运行编译器、类型检查和完整测试。

### 3. 保护已有工作区改动

开始修改前执行 `git status --short`，记录用户未提交文件。能通过新增独立文档或精确修改解决时，
不要格式化、暂存或回退其他文件。功能分支合并后，只有在工作区干净、merge commit 和测试均确认后，
才移除临时 worktree 与已合并分支。

### 4. 推送结果以远端状态为准

推送曾收到并发 ref lock 提示，但错误信息中的远端值已经是目标 merge commit。没有强推，而是先
`git fetch`，比较 `main...origin/main`，确认双方为 `0 0`，再执行幂等推送得到
`Everything up-to-date`。任何并发拒绝都应先核对远端，不能直接 force push。

## 九、失败模式速查

| 失败做法 | 后果 | 正确边界 |
| --- | --- | --- |
| 每次运行重新随机抽题 | 同名套件实际试卷不同 | 固定 manifest 和摘要 |
| 只记录数据集名称 | 无法证明真实版本 | revision、URL、文件 SHA-256 |
| 中文翻译进入 prompt | 偏离英文官方协议 | 中文仅作展示 metadata |
| 未实现的 IFEval 规则按 0 分 | 把工具缺口算成模型失败 | 未知规则直接阻塞 |
| HumanEval 在宿主机执行 | 安全风险且不可审计 | 固定 Docker verifier |
| Docker 缺失记为模型 0 分 | 能力与基础设施混淆 | `blocked`，不进入排名 |
| 只按 sample key 恢复 | 混入旧协议结果 | 同时核对数据和协议指纹 |
| 部分运行进入排行榜 | 不同覆盖率被错误比较 | 完整套件准入门槛 |
| API 透传原始 checkpoint | 泄漏隐藏测试或堆栈 | presentation 允许列表 |
| 冲突直接选一边 | 丢失另一套有效执行路径 | 联合测试驱动语义合并 |
| 测试受限就修改产品逻辑 | 为环境假失败引入回归 | 在正确权限环境复验 |
| 推送冲突后强推 | 覆盖他人提交 | fetch、比较、普通推送 |

## 十、下次新增专业评测集的执行 Checklist

### 产品与统计协议

- [ ] 明确评测对象、能力维度、题量、聚合方式和适用边界。
- [ ] 明确 Mini Suite 不等同官方全量榜单。
- [ ] 固定维度顺序、来源权重和完整运行准入条件。

### 来源与清单

- [ ] 核对许可、上游 revision、下载 URL 和文件 SHA-256。
- [ ] 使用确定性分层抽样，并提交最终 source key manifest。
- [ ] 重建 manifest 后做字节级比较。
- [ ] 下载采用临时文件、摘要验证和原子安装。

### 执行与评分

- [ ] 优先复用 Adapter、Runner、Evaluator 和 Registry。
- [ ] 为特殊规则增加明确 Evaluator，不在通用 Runner 堆数据集分支。
- [ ] 区分模型失败、评分失败和基础设施阻塞。
- [ ] 非可信代码只进入固定、受限、可清理的沙箱。

### 可复现与恢复

- [ ] 创建任务时冻结来源、manifest、提示、生成、评分和 verifier 身份。
- [ ] checkpoint 同时写入并核对协议指纹。
- [ ] 来源或协议漂移时清除受影响的跳过集合。
- [ ] 排名只接受完整且 comparison fingerprint 相同的结果。

### API 与展示

- [ ] readiness 使用共享结构化合同。
- [ ] 英文执行内容与中文展示 metadata 分离。
- [ ] 样本证据包含来源和 source key。
- [ ] 使用允许列表排除隐藏测试、canonical solution、环境和堆栈。

### 验证与交付

- [ ] 先运行相关测试，再运行全部 pytest 和 Ruff。
- [ ] 运行前端测试与生产构建。
- [ ] 显式运行 Docker 集成测试并报告结果。
- [ ] 重建 manifest，运行 `git diff --check`，检查无缓存和数据产物被跟踪。
- [ ] 合并后在目标分支重新验证。
- [ ] 普通推送后 fetch 并确认本地与远端提交一致。

## 结论

专业小型 Benchmark 的核心不是“凑够某个题数”，而是建立一条可审计的比较链：专业来源、固定题目、
英文协议、正确评分、安全执行、可恢复证据、完整排名准入和可重复验证。任何一环缺失，都可能得到
看似精确、实际不可比较的六边形。
