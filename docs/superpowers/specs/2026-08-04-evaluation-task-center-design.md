# EvalHub 评测任务中心设计

## 目标

把当前同步的“评测结果”面板升级为真实的评测任务中心。用户提交评测后立即得到一个持久化任务，能看到排队、运行、完成、失败或取消状态，以及真实样本进度、耗时和资源读数；聚合指标、失败样例与原始 JSON 只在选中任务的详情中展示。

本次实现面向当前单机本地控制台，不引入外部数据库或消息队列。任务历史存入 SQLite，评测由单个后台 Worker 串行执行，为资源归属、Ollama 负载和本地调试提供确定语义。

## 已确认决策

- 任务状态、进度和资源读数必须来自真实后端，不使用前端模拟数据。
- SQLite 数据库存放在 `.runtime/evalhub.db`，服务重启后任务历史仍可查询。
- 同一时间只运行一个评测任务，后续任务按创建顺序排队。
- CPU 与内存采集评测 Worker 进程及其直接子进程；不把整个 EvalHub 服务进程或其他应用混入任务指标。
- GPU 只在平台提供可靠探测能力时显示。无法采集时返回明确的 `supported: false`，前端显示“不支持采集”，不伪造 0%。
- 保留 `/api/evaluations/run` 同步接口，避免破坏 CLI 或已有调用方；新控制台改用任务 API。

## 方案取舍

### 采用：SQLite + 后台单 Worker + HTTP 轮询

创建请求只持久化任务并入队，后台 Worker 执行评测并持续更新进度和资源，前端按任务状态轮询。该方案不依赖额外服务，重启后仍保留历史，模块边界也可在未来替换为 PostgreSQL 和分布式 Worker。

### 未采用：仅前端模拟任务

同步接口在评测结束前没有任何中间状态，模拟进度和资源会误导用户，不能满足“真实任务化”。

### 未采用：Celery + PostgreSQL

这套组合适合多机、多 Worker 和多人共享平台，但会给当前本地控制台增加数据库、Broker、迁移和部署负担，超出本次范围。

## 后端架构

### SQLite 任务仓储

新增独立任务仓储，负责初始化 schema、创建任务、按时间倒序查询、读取详情以及原子更新状态、进度、资源和结果。每次仓储操作使用独立 SQLite 连接，启用 WAL、外键和超时，适配 HTTP 查询线程与后台 Worker 的并发访问。

`evaluation_tasks` 保存：

- 稳定任务 ID、请求 JSON、数据集、模型和适配器；
- `pending`、`running`、`success`、`failed`、`canceled` 状态；
- 已完成样本数、总样本数和 0–100 的派生进度；
- 创建、开始、结束和最近更新时间；
- 当前及峰值 CPU、当前及峰值内存；
- GPU 支持状态、当前及峰值利用率和显存；
- 成功结果 JSON 或失败原因。

列表响应不返回失败样例和原始结果正文，避免任务积累后放大响应；详情响应才包含完整结果。

### 任务调度

任务服务持有 FIFO 队列和一个后台调度线程。提交任务时先写 SQLite，再入队。Worker 每次只启动一个独立评测子进程：

1. 把任务切换为运行态并记录开始时间。
2. 子进程加载数据集、执行 Runner，并通过进程消息队列上报总样本数、完成样本数、成功结果或错误。
3. 父进程定时采集该子进程及直接子进程的 CPU 和 RSS 内存并写入 SQLite。
4. 成功时保存结果并标记完成；异常时保存安全错误信息并标记失败。
5. 取消运行中任务时终止对应评测子进程并标记取消；取消排队任务时保留队列项但在取出时跳过。

服务启动时把上次运行中但未完成的任务标记为失败，原因说明服务重启导致中断；已排队任务从 SQLite 恢复并继续按创建顺序执行。

### 进度回调

`EvaluationRunner.run()` 增加可选的样本完成回调。Runner 在每条样本完成评分并写入结果列表后报告 `(completed_samples, total_samples)`。现有调用方不传回调时行为保持不变。

真实 Benchmark 入口接受可选任务 ID 和进度回调。在样本加载完成后先报告 `(0, total_samples)`，随后由 Runner 上报逐样本进度；最终结果继续使用同一个任务 ID。

### 资源采集

使用 `psutil` 读取评测子进程及其直接子进程：

- CPU：各进程 `cpu_percent` 之和，可超过 100%，表示使用多个逻辑核心；
- 内存：各进程 RSS 之和；
- 峰值：任务生命周期内观测到的最大值；
- 采样间隔：1 秒，足以支持控制台反馈且不会明显增加本地开销。

GPU 探测采用可选能力：首版只在 `nvidia-smi` 可用时读取设备利用率和显存。由于单 Worker 保证同一时间只有一个评测任务，读数明确标注为“任务运行窗口内的活动设备”。Apple Silicon 或其他无法可靠查询的平台返回不支持，不执行推测。

## API 契约

### 创建任务

`POST /api/evaluations`

- 请求体沿用现有 `EvaluationRequest`。
- 返回 HTTP 202 与 `{ "ok": true, "task": TaskSummary }`。

### 任务列表

`GET /api/evaluations`

- 返回 `{ "tasks": TaskSummary[] }`，按创建时间倒序。
- 每项含状态、进度、耗时、当前/峰值资源、结果摘要和错误摘要，不含完整结果。

### 任务详情

`GET /api/evaluations/{task_id}`

- 返回 `{ "task": TaskDetail }`。
- 成功任务包含完整 `EvaluationResult`；其他状态的 `result` 为 `null`。
- 未找到返回结构化 404。

### 取消任务

`POST /api/evaluations/{task_id}/cancel`

- 排队或运行中的任务可取消，返回更新后的任务详情。
- 终态任务保持原状态并返回 409，避免把已完成结果改写为取消。

## 前端信息架构

现有 `ResultPanel` 替换为 `EvaluationTaskPanel`。面板分为两层：

```text
┌ 评测任务 ──────────────────────────────────────────────┐
│ 运行中  GSM8K · qwen2.5   ███████░░  72%   02:14  › │
│ 排队中  MMLU · qwen2.5     等待 1 个任务       00:08  › │
│ 已完成  GSM8K · oracle     5 / 5       0.8000  00:01  › │
├ 选中任务详情 ──────────────────────────────────────────┤
│ 运行轨道：当前样本 / 总样本、进度条、当前阶段          │
│ 遥测：CPU 当前/峰值、内存当前/峰值、GPU 可用状态       │
│ 完成后：聚合指标 → 失败样例 → 原始 JSON                │
└────────────────────────────────────────────────────────┘
```

任务列表始终承担导航职责。点击任务行后才显示详情；未选中任务时自动选择最新任务。运行任务每秒刷新，所有任务进入终态后停止轮询。提交新评测后立即把创建响应插入列表并选中该任务，表单不再等待整个评测完成。

### 视觉方向

延续已有蓝白、边框驱动的控制台，不重新设计其他页面模块：

- 页面背景 `#F7F9FC`、内容面 `#FFFFFF`、主色 `#2563EB`、文字 `#0F172A`、边框 `#E2E8F0`；
- 标题和正文继续使用系统无衬线字体，任务 ID、耗时和资源数值使用现有等宽字体；
- 列表行保持紧凑，状态依靠文字、图标和颜色共同表达；
- 唯一视觉签名是“运行轨道”：细长进度条带一个表示当前样本位置的方形游标，完成后变为连续实线；
- 只为运行游标使用轻微脉冲，遵循 `prefers-reduced-motion`；不增加渐变、大阴影或装饰图表。

窄屏下任务行改为两行卡片式布局，资源指标以两列网格显示，不产生横向滚动。所有任务行使用按钮语义、可见键盘焦点和 `aria-current`；进度使用原生 `progress` 或等价 ARIA 属性。

## 状态与错误

- 无任务：说明提交评测后会在此追踪进度。
- 排队：显示前方任务数量，不展示伪资源值。
- 运行：显示真实进度、动态耗时和最近一次采样资源。
- 成功：显示总耗时、峰值资源和结果摘要；详情中展示聚合指标与失败样例。
- 失败：任务行显示失败，详情给出可诊断错误，不展示结果卡片。
- 取消：保留已完成进度和已采集资源，详情说明由用户取消。
- GPU 不支持：显示“不可用”，并提供“当前平台未提供可靠 GPU 指标”的辅助文字。
- 轮询失败：保留最后一次成功读取的数据，在任务模块内提示刷新失败，不清空历史。

## 测试策略

### Python

- Runner 测试验证逐样本进度回调顺序，同时保护无回调的兼容行为。
- SQLite 仓储测试使用临时目录，验证创建、列表顺序、详情、状态更新、结果持久化和重启恢复。
- 任务服务使用 fake 执行器与 fake 资源采样器，验证 FIFO、成功、失败和取消，不访问网络、不启动 Ollama。
- HTTP 路由测试使用临时 SQLite 与 fake 任务服务，验证创建、列表、详情、取消和结构化错误。

### 前端

- API 测试验证四个任务端点的路径、方法、请求体和错误转换。
- 页面测试验证空状态、提交后立即出现排队任务、运行进度与资源、点击后显示结果、GPU 不支持、失败和取消状态。
- 运行 TypeScript 类型检查、Vitest 和生产构建。

## 文档与兼容性

- 更新 API 草案，标明新任务接口已经实现，并保留同步接口说明。
- 更新系统架构，说明当前 SQLite/单 Worker 的本地任务边界以及未来替换点。
- 更新数据模型文档，补充任务进度、资源和持久化字段。
- 更新本地运行指南，说明数据库位置、历史保留和 GPU 探测限制。
- `.runtime/` 已被忽略或需加入 `.gitignore`，数据库和运行产物不得提交。
- CLI `run-benchmark` 输出与现有同步 API 保持兼容；新增字段只能以可选方式出现。

## 非目标

- 不实现多 Worker、分布式队列、任务优先级或重试策略。
- 不采集 token、费用、温度、风扇或功耗。
- 不新增任务筛选、分页、批量删除或导出。
- 不保证 Apple Silicon GPU 指标；无法可靠采集时明确降级。
- 不迁移现有内存 Registry 到 SQLite；本次 SQLite 只持久化控制台评测任务。

## 验收标准

- 提交评测在任务创建后立即返回，不再阻塞浏览器等待整个 Benchmark。
- 任务按 FIFO 串行运行，进度与已完成样本数真实一致。
- 服务重启后能读取历史；中断任务状态明确，排队任务能恢复。
- 运行任务展示真实耗时、CPU、内存和可用时的 GPU 指标。
- 点击任务才显示结果详情，列表响应不携带完整结果。
- 同步 API 和 CLI 仍兼容。
- Python、前端测试、Ruff、类型检查、生产构建和 `git diff --check` 全部通过。
