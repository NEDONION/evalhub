# EvalHub 全量 Python 中文注释设计

## 背景

仓库根目录的 `AGENTS.md` 已要求新增或修改的 Python 方法提供详细中文 docstring，且函数或
方法体内任意连续有效代码不得超过 5 行而没有详细中文注释。本任务把同一标准一次性应用到
现有 Python 代码，并在验证通过后推送到远端 `main`。

当前工作区共有 36 个 Python 文件、约 1,674 行代码，覆盖领域模型、评测引擎、适配器、数据集、
Registry、CLI、HTTP 服务、配置、入口脚本和测试。执行基线包含 `src/evalhub/ollama.py`、
`src/evalhub/server.py`、`tests/test_ollama_status.py` 与新增的 `tests/test_server_frontend.py`；用户已
授权将现有 Python 工作区修改与注释一起提交。

## 目标

- 为仓库内全部现有 Python 模块补充准确、详细的中文模块 docstring。
- 为全部类、函数、同步方法和异步方法补充与实际行为一致的详细中文 docstring。
- 在函数和方法体的逻辑边界添加详细中文注释，保证任意连续有效代码不超过 5 行。
- 修复阻止仓库级 Ruff 检查通过的轻量风格问题，但不改变业务语义。
- 保持现有测试行为，通过 Ruff、pytest 和专用注释完整性检查。
- 将最终结果安全合并到本地 `main` 并无强制推送地更新远端 `main`。

## 范围

包含：

- `src/evalhub/**/*.py`
- `tests/**/*.py`
- `run_evalhub.py`

排除虚拟环境、缓存、构建产物和 `.worktrees/` 中的其他工作区。HTML、CSS、TypeScript、Shell、
Markdown 与配置文件不纳入本次注释改造；除本设计、实现计划和必要的 Git 忽略维护外，不修改
这些文件。

## 方案选择

采用逐文件人工语义化注释方案。

- 相比机械按行插入，它能把注释放在完整表达式和逻辑边界，不会拆坏语法或制造无意义文字。
- 相比仅补 docstring，它能够满足每最多 5 行有效代码提供一次解释的既定规则。
- 相比自动生成统一模板，它能根据领域实体、适配器、评测器、数据加载和 HTTP 请求处理的实际
  职责写出有信息量的说明。

## 注释标准

### 模块和类

- 每个 Python 文件以中文模块 docstring 说明模块职责、主要边界和重要副作用。
- 每个类提供中文类 docstring，说明它表达的领域概念、承担的职责或测试用途。
- 数据类与枚举说明关键字段或状态含义，但不重复逐字罗列显而易见的声明。

### 函数和方法

- 每个 `def` 和 `async def` 都提供中文 docstring，包括私有函数、测试方法、协议方法、抽象方法
  和 dunder 方法。
- docstring 首段说明用途和行为；存在参数、返回值或可预期异常时，分别用中文 `Args`、
  `Returns`、`Raises` 段说明。
- 无参数、无返回值且不会主动抛出业务异常的方法不添加空的模板段落。
- 协议和抽象方法保留原有接口语义，只把单行省略号形式展开为 docstring 加省略号的方法体。

### 行内注释密度

- 在每个函数或方法体内，以物理有效代码行为计数单位；空行、注释和 docstring 行不计数。
- 中文 docstring 结束后重新计数；任意连续有效代码不得超过 5 行而没有详细中文注释。
- 注释放在完整逻辑块之前，说明其目的、业务意义、约束、容错原因或状态变化。
- 多行表达式、装饰器、函数签名、字符串和链式调用视为不可拆分单元，不在其中插入注释；需要时
  在该单元之前添加说明。
- 禁止“执行下面代码”“处理数据”“返回结果”等不能增加理解的信息。
- 导入块不按 5 行规则机械拆分，保持 Ruff 的导入分组；模块级常量和大型字面量按语义分组添加
  中文章节注释。

## Ruff 修复边界

当前 Ruff 问题包含导入排序、入口脚本的延迟导入、超长行和泛型 Registry 中的常量属性访问。
处理方式如下：

- 使用 Ruff 认可的导入顺序，不改变导入对象。
- `run_evalhub.py` 必须先修改 `sys.path` 再导入包入口，保留该行为并用中文原因说明及精确的
  `noqa` 标记处理 `E402`。
- 超长表达式只做等价换行。
- 泛型 Registry 保留运行时按 `id` 取值的现有行为；如需要抑制 `B009`，使用精确标记并以中文
  说明协议边界，避免无关类型架构调整。
- 不使用全文件忽略，也不顺手重构业务逻辑。

## 用户现有修改

- 先只提交用户已授权纳入的 `src/evalhub/ollama.py`、`src/evalhub/server.py`、
  `tests/test_ollama_status.py` 与 `tests/test_server_frontend.py` 当前内容，建立可追踪的实现基线。
- 不暂存或提交其他现有的前端、脚本、文档或工作区修改。
- 后续在隔离工作区基于该基线补充全量注释，避免和其他进行中的工作相互覆盖。

## 验证

### 自动检查

- `.venv/bin/python -m ruff check .`
- `.venv/bin/python -m pytest`
- 使用一次性 AST/tokenize 检查器验证：
  - 每个目标模块、类、函数和方法都有包含中文的 docstring；
  - 每个函数或方法体不存在超过 5 行的未解释有效代码段；
  - 检查器只读取仓库文件，不写入或修改源码。

### 人工检查

- 逐文件阅读 diff，确认注释描述与实现一致，不包含敷衍语句或错误承诺。
- 检查除批准的两份现有修改和 Ruff 等价修复外，没有业务逻辑变化。
- 检查提交范围不包含用户其他未提交文件、缓存、数据集、报告或密钥。

## Git 与推送

- 在隔离分支完成注释改造和验证，使用明确提交保存变更。
- 合并回本地 `main` 前确认与其他未提交文件无冲突，并在合并结果上重新运行验证。
- 推送前获取远端状态；仅执行普通 push，不使用 force push。
- 若远端 `main` 已前进，安全整合远端提交、重新验证后再推送。
- 推送成功后确认本地 `main` 与 `origin/main` 指向一致或本地仅包含明确允许的后续提交。

## 完成标准

- 36 个目标 Python 文件全部通过中文 docstring 与注释密度检查。
- Ruff 零错误，pytest 全部通过。
- 注释内容详细、准确，并且没有改变现有业务行为。
- 用户授权的两份 Python 修改已纳入，其他未提交修改保持原样。
- 最终提交已安全推送到远端 `main`，且没有使用强制推送。
