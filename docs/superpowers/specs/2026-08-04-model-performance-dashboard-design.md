# 模型历史成绩与任务类型分区设计

## 目标

在现有评测任务中心中清楚区分模型评测与 Agent 评测，并新增独立的“模型成绩”工作区，按同一 Benchmark 或同一 Suite 聚合 SQLite 历史任务，让用户直观看到模型排名、最好成绩、最新成绩和历史趋势。

## 范围与口径

- 任务中心提供“全部 / 模型评测 / Agent 评测”筛选，任务行显示明确类型标签。
- 模型成绩只统计 `evaluation_type=model` 且具有有效结果摘要的任务。
- 单 Benchmark 任务按 `benchmark:<dataset>` 分组，Suite 任务按 `suite:<suite_id>` 分组；不同范围绝不混排。
- 每个模型的排行榜成绩取所选范围内历史最高 `average_score`。
- 一次运行的分数严格高于该模型此前所有同范围成绩时，标记为“刷新纪录”；首条有效成绩是初始纪录，不显示提升幅度。
- Agent 评测保留在任务中心，不进入模型排行榜，避免两种评分协议产生误导性比较。

## 信息架构

侧栏新增“模型成绩”，与“评测结果”并列：

- “评测结果”继续负责单次任务的排队、进度、资源、节点和完整结果。
- “模型成绩”只负责跨任务、按模型聚合的历史比较。

任务中心顶部使用分段筛选器，切换类型时选择该分组的第一条任务。若该类型为空，展示引导性空状态，不影响后台任务执行。

模型成绩页由四部分构成：

1. 范围选择器：在已有可比较 Benchmark 与 Suite 之间切换。
2. 摘要轨道：显示参评模型数、有效运行数、当前第一名和最近刷新纪录的模型。
3. 横向排行榜：按历史最高分降序展示模型，附最新成绩、运行次数和与第一名差距。
4. 历史趋势：选择一个模型后，以时间顺序展示每次有效成绩，并突出刷新纪录节点。

## 数据接口

新增只读接口：

```http
GET /api/model-performance?scope=benchmark:gsm8k
```

不传 `scope` 时，后端选择有效运行次数最多的范围；次数相同时按稳定键排序。响应包含：

- `scopes`：可选范围、显示名称、类型和有效运行数。
- `selected_scope`：当前范围，或无历史时为 `null`。
- `models`：按最佳分排序的模型聚合，包含最佳/最新成绩、运行次数、最佳任务、时间和完整历史点。
- `record`：最近一次刷新既有最好成绩的历史点；没有提升纪录时为 `null`。

历史点包含任务 ID、成绩、完成时间、是否为当时纪录和相对前纪录的提升值。API 不返回完整任务结果或失败样本。

## 后端边界

- SQLite 仓储增加只读历史摘要查询，只读取聚合所需列，不加载完整 `result_json`。
- 纯聚合函数负责范围分组、排序、纪录判断和响应模型，便于确定性单元测试。
- 服务层暴露模型成绩查询；HTTP 层只解析 `scope` 并转换未找到范围的错误。
- 不新增第三方依赖，不新增冗余汇总表，不改变现有任务写入和执行语义。

## 前端设计

沿用 EvalHub 的白底、蓝色主色与紧凑数据密度，增加两种有业务含义的强调色：翠绿色表示“刷新纪录”，琥珀色表示 Agent 类型。排行榜使用蓝色水平量尺，趋势图使用深蓝折线与绿色纪录点。

页面的标志性元素是“纪录轨道”：排行榜和趋势图共享同一 0–100% 视觉刻度，用户不需要在不同图表间重新理解比例。图表使用原生 SVG 和可读文本双重表达，键盘与屏幕阅读器仍能访问所有成绩。

移动端将排行榜保持纵向，趋势图允许水平滚动或压缩到最少 320px；任务筛选器保持三段等宽，不改变现有移动端侧栏行为。

## 空态与错误处理

- 没有任何模型结果：提示先完成模型评测，并提供前往“发起评测”的操作。
- 当前范围只有一个模型：仍展示历史趋势，并明确“暂无其他模型可比较”。
- 当前模型只有一次成绩：展示单点和“首次成绩”，不伪造趋势。
- API 返回不存在的范围：返回 `400` 和稳定错误消息，前端保留上一次可用数据并展示可恢复提示。
- 活动任务完成后，现有轮询刷新任务列表，同时重新读取模型成绩，让新纪录无需手动刷新即可出现。

## 验证

- Python 单元测试覆盖范围隔离、Agent 排除、最佳分排序、并列、纪录提升、默认范围和空历史。
- API 测试覆盖默认查询、指定范围和未知范围错误。
- 前端测试覆盖任务类型筛选、类型标签、成绩空态、范围切换、排行榜顺序和纪录标记。
- TypeScript 类型检查、前端生产构建、Ruff、完整 pytest 与 `git diff --check` 必须通过。
